# خطة تنفيذية لتسريع AMIC والكاش الخادمي لبيانات السوق

**الحالة:** مقترح للتنفيذ المحلي أولًا.  
**النطاق:** تسريع التصفح وبيانات السوق والتحليل الفني، مع الحفاظ على دقة المصدر ووقت الجلب وعزل بيانات كل مستخدم.  
**خارج النطاق:** لا تداول حقيقي، ولا تخزين لمحتوى المحادثات أو المفاتيح، ولا نشر جديد قبل موافقة عربية صريحة منفصلة.

## 1. الهدف والنتيجة المستهدفة

تهدف الخطة إلى تقليل زمن فتح الصفحات وتكرار طلبات مزودي البيانات، مع عدم عرض بيانات مخزنة على أنها لحظية. تعتمد النتيجة على ثلاثة مبادئ: **لا تجلب البيانات نفسها مرتين بلا حاجة**، و**لا تنتظر المصدر الخارجي عندما تكفي قراءة قريبة وآمنة**، و**أظهر دائمًا المصدر ووقت الجلب وحالة القِدم**.

| المجال | الوضع بعد التحسين الحالي | ما تستكمله هذه الخطة |
|---|---|---|
| تحميل الواجهة | صفحات محمّلة كسولًا، وحزمة الدخول انخفضت محليًا من 3.16 MiB إلى 0.72 MiB | قياس زمني حقيقي ومواصلة فصل الحمولات النادرة |
| استعلامات العميل | ذاكرة مشتركة لمدة 30 ثانية وتعطيل إعادة الجلب العامة عند العودة للنافذة | إلغاء الطلبات القديمة، ومؤشرات أداء دقيقة، وسياسات خاصة بكل صفحة |
| بيانات السوق | كاش لقطات قائم جزئيًا وخدمات مزودين متعددة | خدمة كاش موحدة، منع ازدواج الجلب، وتحديث في الخلفية |
| التحليل الفني | تأجيل بطاقات ثانوية حتى الاقتراب منها | مشاركة مدخلات الشموع بين الشارت والتحليل والتوافق |

## 2. مؤشرات القبول قبل بدء التحسينات الخادمة

لا تُعتمد أهداف زمنية جامدة قبل القياس الحي، لأن زمن مزود البيانات والشبكة يختلفان. لكن يجب جمع الخط الأساس لكل من فتح الصفحة، أول بيانات مفيدة، وزمن كل استدعاء tRPC.

| المؤشر | طريقة القياس | معيار القبول الأولي |
|---|---|---|
| وقت فتح المسار | Web Vitals في المتصفح مع اسم المسار | تحسن قابل للقياس عن الخط الأساس بدون تراجع في التفاعل |
| زمن `market.candles` و`market.analysis` | قياس خادمي بالمللي ثانية مع نوع النتيجة | ارتفاع نسبة نتائج الكاش وانخفاض الاتصالات الخارجية المكررة |
| نسبة إصابات الكاش | `cacheHit / (cacheHit + cacheMiss)` لكل نوع بيانات | تقرير مرئي، لا نسبة مستهدفة قبل توفر بيانات فعلية |
| أعمار البيانات | `fetchedAt` و`cachedAt` و`isStale` | لا استجابة سوقية بلا وصف مصدر ووقت واضحين |
| طلبات متزامنة مكررة | عداد انتظار نفس المفتاح | طلب خارجي واحد للمفتاح المتطابق أثناء الجلب |

## 3. المرحلة الأولى — القياس الحي الآمن

تضاف طبقة قياس خفيفة لا تسجل رموز الجلسات أو رسائل المستخدم أو مفاتيح المزودين. تسجل فقط نوع المسار، اسم إجراء tRPC، زمن الاستجابة، رمز النتيجة، ووسم مصدر البيانات وحالة الكاش. تعرض البيانات للمسؤول في لوحة تشغيلية مختصرة أو سجل خادمي مجمع.

### خطوات التنفيذ

1. إضافة مقياس زمني إلى مسارات السوق الرئيسية: الشموع، التحليل، نبضة السوق، الماسح، والتوافق متعدد الأطر.
2. إرسال مؤشرات Web Vitals مجمعة من العميل دون ربطها بمحتوى المستخدم أو المحادثة.
3. تمييز كل استجابة سوقية بـ `source`, `fetchedAt`, `cachedAt`, `cacheStatus`, و`isStale` عندما ينطبق ذلك.
4. إعداد لوحة مراقبة إدارية مختصرة تعرض الوسيط وP95 ونسبة الكاش حسب نوع البيانات، من دون عرض `userId` أو نصوص أو مفاتيح.

### معايير القبول

يجب أن يكون القياس خاملاً عند فشله، وألا يمنع الاستجابة الأساسية، وأن يمر باختبارات تفصل القياس عن محتوى المستخدم.

## 4. المرحلة الثانية — خدمة كاش خادمية موحدة

تنشأ خدمة واحدة مثل `server/marketCache.ts`، ولا يوضع منطق الكاش متفرقًا داخل كل Router. تكون خدمة المزود مسؤولة عن الجلب، والـRouter مسؤولًا عن التحقق والتفويض، وخدمة الكاش مسؤولة عن المفاتيح والصلاحية والتزامن والبيانات الوصفية.

### عقد البيانات المقترح

```ts
type CachedMarketValue<T> = {
  value: T;
  source: string;
  fetchedAt: Date;
  cachedAt: Date;
  expiresAt: Date;
  cacheStatus: "memory" | "snapshot" | "fresh" | "stale-revalidate";
  isStale: boolean;
};
```

### بناء مفتاح الكاش

يبنى المفتاح من جميع المدخلات التي تغير النتيجة، بعد التطبيع إلى أحرف كبيرة/صغيرة موحدة:

| نوع النتيجة | مثال مفتاح |
|---|---|
| الشموع | `candles:BINANCE:BTCUSDT:1h:limit=300` |
| التحليل | `analysis:BINANCE:BTCUSDT:1h:contract=v1` |
| التوافق | `multi-timeframe:FX:XAUUSD:frames=15m,1h,4h,1D,1W` |
| نبضة السوق | `overview:cryptoGainers:source=v1` |
| الماسح | `screener:BINANCE:1h:rating=all:limit=20` |

لا يدخل `userId` في مفاتيح النتائج العالمية. أما الإعدادات والقوائم والتنبيهات والصفقات الورقية فهي بيانات خاصة، وتبقى في جداولها المعزولة ولا تستخدم كاش سوقي عالميًا.

### طبقات الكاش

| الطبقة | مسؤوليتها | سياسة الإخلاء |
|---|---|---|
| ذاكرة العملية | أسرع إجابة ومنع التزامن المكرر داخل مثيل التطبيق | حد أقصى للحجم + انتهاء TTL |
| `marketSnapshots` | مشاركة لقطة بين المثيلات وإتاحتها بعد إعادة التشغيل | فهارس زمنية وتنظيف المهمة المجدولة للقطات المنتهية فقط |
| المزود الخارجي | المصدر عند غياب لقطة صالحة | لا يستدعى إلا عند الحاجة أو تحديث صريح |

### منع ازدواج الطلبات المتزامنة

تحتفظ الخدمة بخريطة `inFlight` من `cacheKey` إلى `Promise`. إن طلب الشارت والتحليل البيانات نفسها في الوقت ذاته، ينضم الطلب الثاني إلى الـPromise نفسه بدل إنشاء اتصال إضافي بالمزود. يجب حذف المفتاح من الخريطة في `finally` حتى عند الخطأ.

### القراءة القديمة الآمنة مع تحديث خلفي

عند انتهاء الصلاحية حديثًا، يمكن إعادة لقطة قريبة مع `isStale: true` وتشغيل تحديث واحد في الخلفية. تستخدم هذه السياسة للصفحات الاستكشافية فقط، ولا تستخدم عندما يطلب المستخدم تحديثًا صريحًا أو عندما تتجاوز اللقطة حد العمر الأقصى. لا تسمى النتيجة «حالية» إذا كانت قديمة.

## 5. المرحلة الثالثة — سياسة صلاحية حسب نوع السوق والإطار

| البيانات | TTL للذاكرة | نافذة القراءة القديمة القصوى | ملاحظات |
|---|---:|---:|---|
| اقتباس حي | 2–5 ثوانٍ | لا تستخدم افتراضيًا | يعرض مصدر السعر ووقته دائمًا |
| شموع 1m–5m | 15–30 ثانية | 30 ثانية | يحترم البث الحي حيث يتوفر |
| شموع 15m–1h | 60–120 ثانية | 3 دقائق | مناسبة للتحليل الاعتيادي |
| شموع 4h–1D | 5–15 دقيقة | 30 دقيقة | يقل التغير الفعلي بين الطلبات |
| شموع أسبوعية/تاريخية | 30–60 دقيقة | ساعتان | لا حاجة لجلب متكرر |
| التحليل المشتق | يرتبط بعمر الشموع وإصدار العقد | نفس حد الشموع أو أقل | يعاد عند تغير المدخلات أو نسخة الخوارزمية |
| نبضة السوق والماسح | 1–5 دقائق | 10 دقائق | يعتمد على مزود السوق ونوع العرض |

هذه القيم مبدئية، وتراجع بعد جمع مؤشرات الإصابات والانتظار الفعلية. تحفظ سياسة TTL في ملف إعدادات مركزي، لا كسلاسل أرقام موزعة في الملفات.

## 6. المرحلة الرابعة — إدماج تدريجي حسب المخاطر

| الترتيب | المسار | السبب | شرط الانتقال |
|---:|---|---|---|
| 1 | `market.candles` | أكبر مدخل مشترك للشارت والتحليل والتوافق | اختبارات مفتاح/TTL/التزامن وبيانات وصفية صحيحة |
| 2 | `market.analysis` | مشتق من الشموع ويستفيد من عدم التكرار | مقارنة ناتج الكاش بالناتج المباشر |
| 3 | نبضة السوق ولقطات النظرة العامة | متعددة الطلبات ومتكررة بين المستخدمين | التحقق من عدم اختلاط الأقسام أو المصدر |
| 4 | الماسح والتوافق متعدد الأطر | تكلفة أعلى وعدة أطر زمنية | حدود واضحة للمدخلات وحجم النتائج |
| 5 | المصادر الثانوية | توسعة بعد ظهور قياسات حقيقية | لا زيادة في الأخطاء أو اللقطات القديمة |

لا تُنقل كل المصادر دفعة واحدة. تنشر كل مرحلة مستقلة بعد اختبارات ومراجعة أثرها، وتبقى إمكانية تعطيل الكاش لنوع واحد عبر إعداد خادمي أو علم ميزة.

## 7. المرحلة الخامسة — تحسينات العميل والنقل

### العميل

1. إلغاء طلبات الرمز أو الإطار القديم عند اختيار جديد سريعًا، وعدم قبول الاستجابة إذا لم تعد مطابقة للمعلمات النشطة.
2. إعادة استخدام بيانات الشموع بين الشارت وبطاقات التحليل عبر cache key موحد في tRPC/TanStack Query.
3. استخدام القوائم الافتراضية للتنبيهات والإشارات والصفقات عندما يزيد العدد عن حد معلن.
4. الاحتفاظ بالتحميل الكسول الحالي، والتحقق من أن مكتبات الدردشة والمخططات لا تنتقل إلى الحزمة الأساسية.
5. المحافظة على مؤشرات تحميل مكانية بدل حجب الواجهة كلها.

### النقل والإنتاج

1. ضبط Caddy على ضغط Brotli وGzip حيث يكون مناسبًا.
2. إعطاء ملفات `/assets/` ذات البصمة Cache-Control طويل الأجل و`immutable`.
3. إبقاء HTML قصير العمر حتى يرى المستخدم إصدارًا جديدًا بعد النشر.
4. التحقق من HTTP/2 أو HTTP/3 بحسب إعداد Caddy الحالي، من دون تغيير أمني غير مدروس.
5. عدم وضع أسرار أو استجابات tRPC الخاصة في cache عام على الحافة.

## 8. المرحلة السادسة — قاعدة البيانات وتشغيل IBM

تُجمع الاستعلامات البطيئة أولًا ثم تفحص بـ `EXPLAIN` على قاعدة إنتاج آمنة. تضاف الفهارس فقط إذا دعمتها أنماط الاستعلام الفعلية، خصوصًا لجداول التنبيهات والصفقات واللقطات. لا يُستخدم فهرس جديد لمجرد التخمين، ولا تنفذ عمليات تغيير مدمرة خلال هذه الدفعة.

تتأكد عملية النشر إلى IBM من أن الترحيلات تعمل قبل تشغيل النسخة الجديدة كلما تغير المخطط. لا تعدل مهمة تنظيف `marketSnapshots` أو الجداول القديمة غير المستخدمة ضمن هذه الخطة ما لم يكشف القياس حاجة مباشرة.

## 9. الاختبارات المطلوبة

| الطبقة | الاختبارات |
|---|---|
| خدمة الكاش | تطبيع المفتاح، TTL، إصابة/فقدان الكاش، انتهاء الصلاحية، القراءة القديمة، حذف `inFlight` بعد النجاح والفشل |
| العزل | منع تخزين البيانات الخاصة ضمن مفاتيح عامة، وعدم تسريب إعدادات أو تنبيهات بين الحسابات |
| Router | استجابة البيانات الوصفية، التحديث الصريح، سلوك المزود عند الفشل |
| العميل | إلغاء/تجاهل طلب قديم عند تغيير الرمز، وعدم إعادة الجلب غير الضروري، حالات التحميل والخطأ |
| الأداء | مقارنة قبل/بعد لحجم الحزمة، وعدد الطلبات، وزمن الاستجابة باستخدام بيانات حقيقية أو سجلات قياس |
| الإنتاج | تحقق من الصحة، قراءة مصدر ووقت الجلب، ومراقبة الأخطاء بعد النشر |

## 10. المخاطر والضوابط

| الخطر | الضابط |
|---|---|
| عرض بيانات قديمة كأنها حية | إظهار `source` ووقت الجلب ووسم `isStale` بوضوح |
| تضارب نتائج التحليل بعد تحديث الشموع | تضمين الإطار والحد ونسخة العقد ووقت المصدر في المفتاح |
| تضخم ذاكرة المثيل | حد حجم LRU/TTL وتنظيف في `finally` وعدم تخزين نتائج ضخمة بلا سقف |
| ضغط مفاجئ على المزود بعد انتهاء TTL | منع التزامن وقراءة قديمة آمنة وتوزيع انتهاء الصلاحية عند الحاجة |
| تسريب بيانات مستخدم | فصل كاش السوق العالمي عن بيانات الحساب تمامًا |
| تحسن نظري بلا أثر فعلي | لا تعميم أو نشر واسع قبل القياس الحي ومقارنة المؤشرات |

## 11. التسلسل المقترح للبدء

1. إضافة القياس الخادمي والعميل مع لوحة إدارية مختصرة.
2. تنفيذ `marketCache` واختبارها مستقلًا دون ربطها بأي Router.
3. ربط الشموع أولًا، ثم التحليل الفني، مع علم ميزة تعطيل سريع.
4. قياس الأثر في بيئة محلية ثم إنتاج محدود بعد الموافقة.
5. ربط نبضة السوق والماسح والتوافق بعد ثبات الشموع والتحليل.
6. تحسين Caddy وفهارس قاعدة البيانات بناءً على البيانات المقاسة.

> نقطة القرار الأولى: لا يبدأ ربط كل مسارات السوق بالكاش قبل نجاح الشموع في منع التكرار مع بقاء المصدر والوقت وحالة القِدم واضحة للمستخدم.
