# دمج اختبارات بطاقة «ملخص الأدلة» في CI/CD

## الوضع الحالي

يحتوي مسار `.github/workflows/deploy-ibm.yml` على وظيفة `verify` تشغّل `pnpm test` ثم `pnpm check` ثم `pnpm build`. ولا تبدأ وظيفة `deploy` إلا بعد نجاح `verify`، لذلك فإن أفضل مكان لحاجز اختبارات البطاقة هو وظيفة التحقق نفسها أو وظيفة إضافية تعتمد عليها قبل النشر.

## طبقات الاختبار

### اختبارات منطقية حتمية

تختبر Vitest الدالة النقية التي تستقبل عقد `UnifiedDecisionSummary` وتعيد الحالة والنصوص والألوان والمساهمات المرئية. يجب تغطية حالات التوافق الصاعد والهابط، التعارض، حجب بوابة ICT، نقص البيانات، وغياب السياق المترابط. هذه الاختبارات لا تحتاج قاعدة بيانات أو أسرارًا أو اتصالًا بمزود السوق.

### اختبارات مكوّن البطاقة

تختبر الواجهة أن شارة الحالة ودرجة الجودة ودرجة التغطية وتفاصيل الركائز تظهر من العقد نفسه. يفضّل استخدام React Testing Library مع بيئة `jsdom`، وتمرير fixtures ثابتة إلى البطاقة بدل استدعاء tRPC. بهذه الطريقة لا تتأثر اختبارات الواجهة بتأخر السوق أو جلسة المستخدم أو تغير مزود البيانات.

تتأكد الاختبارات أيضًا من وجود `role="status"` أو `aria-live` للتحديثات غير الخطرة، و`role="alert"` لحالات نقص البيانات المؤثرة، ومن أن النص يوضح التعارض دون الاعتماد على اللون وحده. ويجب اختبار فتح وإغلاق قسم «عرض الأسباب» بلوحة المفاتيح.

### اختبارات المتصفح والمرئيات

يضاف اختبار Playwright محدود لتشغيل الصفحة محليًا أو تشغيل مكوّن البطاقة في مسار اختبار داخلي، مع اعتراض طلبات الشبكة وإرجاع fixtures ثابتة. يغطي الاختبار سطح المكتب بعرض RTL، وهاتفًا بعرض 375 بكسل، ويفتح تفاصيل الركائز ويتحقق من عدم خروج النص أو ظهور تمرير أفقي. يمكن حفظ لقطات مرجعية للحالات الرئيسية، لكن لا ينبغي جعل لقطة واحدة معيارًا وحيدًا لقبول التغيير بسبب اختلاف الخطوط والمنصات.

لا يستخدم هذا الاختبار الإنتاج الحقيقي ولا حسابًا شخصيًا. فإذا احتاجت صفحة التحليل إلى المصادقة، يُختبر المكوّن بمعزل عن جلسة الإنتاج أو يُستخدم حساب CI وقاعدة بيانات مؤقتة لا تحتوي بيانات مستخدمين حقيقية.

## بنية GitHub Actions المقترحة

يفضل فصل التحقق عن النشر مع إبقاء النشر محجوزًا لفرع `main`:

```yaml
name: AMIC CI

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 25
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: corepack enable
      - run: pnpm install --frozen-lockfile
      - name: Unit and server tests
        env:
          JWT_SECRET: ci-test-session-secret-not-for-production
        run: pnpm test
      - name: UI component tests
        run: pnpm test:ui
      - name: Browser smoke and accessibility tests
        run: pnpm test:e2e
      - name: TypeScript
        run: pnpm check
      - name: Production build
        run: pnpm build
      - name: Upload browser artifacts on failure
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: ui-test-report
          path: |
            playwright-report/
            test-results/
```

تضاف في `package.json` أوامر واضحة مثل `test:ui` و`test:e2e`. إذا كانت اختبارات Playwright ستستخدم متصفح Chromium، يضاف في خطوة مستقلة `pnpm exec playwright install --with-deps chromium`، ويفضل تنفيذها في وظيفة مستقلة أو الاستفادة من cache لتقليل زمن CI.

## ربطه بالنشر الحالي

في الوضع الحالي يكفي إضافة `pnpm test:ui` و`pnpm test:e2e` إلى وظيفة `verify` الموجودة؛ فوظيفة `deploy` تعتمد عليها أصلًا. والأفضل على المدى المتوسط إنشاء workflow قابل لإعادة الاستخدام، بحيث يستدعيه كل من فحص Pull Request والنشر، لتجنب اختلاف الاختبارات بين المسارين. لا ينبغي وضع مفاتيح IBM أو مفاتيح السوق في اختبارات البطاقة؛ تبقى أسرار النشر داخل وظيفة `deploy` فقط.

إذا أريد منع النشر التلقائي عند فشل اختبارات المتصفح، يبقى الشرط صريحًا: `deploy.needs: verify`. أما إذا كانت اختبارات المرئيات تجريبية أو غير مستقرة، فلا توضع كحاجز نشر قبل معالجة عدم استقرارها؛ يمكن رفع تقريرها كتحذير منفصل، بينما تبقى اختبارات المنطق والوصول وبناء الإنتاج حواجز إلزامية.

## استراتيجية fixtures

تُحفظ fixtures صغيرة ومقنعة مثل `alignedBullish`, `conflicted`, `needsConfirmation`, و`insufficientData` في ملفات اختبار TypeScript. لا تتضمن أسعار مستخدمين أو مفاتيح أو بيانات سوق حية، ولا تستخدم تقييمات أو شهادات مستخدمين مصطنعة. كل fixture يصرح بحداثة البيانات وتغطيتها، حتى يختبر CI العلاقة بين الحالة المعروضة وسببها.

## اختبارات القبول الأساسية

| الحالة | تحقق CI |
|---|---|
| توافق صاعد | تظهر الحالة والنص ودرجة التغطية ومساهمتا الأساس وICT |
| توافق هابط | يتغير الاتجاه والنص دون اعتماد على اللون وحده |
| تعارض الأساس وICT | تظهر «عوامل متعارضة» ولا تظهر صياغة شراء/بيع حاسمة |
| بوابة ICT حاجبة | تظهر «يحتاج تأكيدًا» وسبب الحجب |
| سياق مترابط غير متاح | تنخفض التغطية دون فشل البطاقة أو تغيير النتيجة الأساسية صامتًا |
| بيانات غير كافية | تظهر رسالة المصدر/الحداثة وزر التحديث أو الإجراء المناسب |
| هاتف RTL | لا يوجد قص للنص أو تمرير أفقي، والتوسيع يعمل باللمس ولوحة المفاتيح |
| إعادة التصيير | لا تتغير النتيجة أو ترتيب الركائز بسبب ترتيب خصائص الكائن |

## قواعد الاعتماد

لا تعتبر البطاقة جاهزة للدمج إلا إذا نجحت اختبارات Vitest الحالية، واختبارات مكوّن البطاقة، وفحص TypeScript، وبناء الإنتاج. ويكون اختبار المتصفح إلزاميًا بعد استقرار بيئة Chromium. تحفظ تقارير الفشل كلقطات وtrace داخل GitHub Actions دون تضمين cookies أو أسرار أو بيانات حسابات حقيقية.

## مسار التنفيذ المقترح

يبدأ التنفيذ بإضافة عقد fixtures واختبارات Vitest للمكوّن، ثم إضافة اختبار متصفح واحد لحالة التوافق وحالة التعارض على RTL، ثم ربط الأوامر بوظيفة `verify`. بعد نجاح ذلك تضاف لقطات الهاتف والحاسوب كتحقق مساعد، ثم يعاد تشغيل workflow كامل على Pull Request قبل السماح لأي دفع إلى `main`. لا يحتاج هذا التصميم إلى قاعدة بيانات جديدة أو تغيير في منطق التداول الورقي.
